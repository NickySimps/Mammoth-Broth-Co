# Commerce backend API contract

All money is USD integer cents. Firebase v1 callables accept plain objects, return the objects below. Never write orders from a browser. Only a verified Stripe webhook marks an order paid. A browser Stripe success is NOT payment confirmation.

## Immediate frontend coordination — security contract change

Both creation callables now require `receiptToken` supplied BEFORE the first network attempt: generate 32 bytes with browser `crypto.getRandomValues(new Uint8Array(32))`, encode exactly 64 lowercase hex characters, and persist it together with the random `requestId` and frozen request payload before calling. Reuse the identical token/payload/requestId after ANY error. Responses echo only the supplied proven token, including retries; never mint a replacement to retry an existing ID. No raw token may enter logs/analytics. Existing orders cannot be recovered from requestId/email alone.

Both creation callable entrypoints use Firebase v1 `runWith({enforceAppCheck:true})`: missing/invalid App Check tokens are rejected by the SDK before business logic. This applies to guests, signed-in customers and creation retries; Firebase Auth is not a bypass. The core also requires SDK-verified `context.app.appId` before a new order. Initialize Firebase App Check on the same Firebase app before creation, with `initializeAppCheck(app, {provider: new ReCaptchaEnterpriseProvider(OWNER_PROVISIONED_SITE_KEY), isTokenAutoRefreshEnabled:true})`; use the existing Firebase HTTPS callable SDK, which attaches the token. The site key/provider registration and production domain allowlist must be provisioned by the owner; none is invented here. If unavailable, show ordering unavailable, not success. This is an explicit new prerequisite for authenticated customer creation too; existing admin operations, receipt reads, quotes and webhook keep their previous authorization and do not require App Check. Never put a token/appId in request data as a substitute for SDK verification.

## Frontend security implementation / configuration blocker

`commerce-config.mjs` exports `COMMERCE_APP_CHECK_SITE_KEY = ''` intentionally: **all creation is unavailable until the owner provisions a real public reCAPTCHA Enterprise website key**, registers the same key/web app in Firebase App Check, and configures the production domain allowlist. No external account was configured and no live attestation was verified. A key-shaped value alone is not evidence of successful registration. There is no shipped fake key, secret, debug bypass, or authenticated-creation bypass.

`store.js` keeps all Firebase CDN modules at **9.6.1**. Enterprise is supported: the [official release notes](https://firebase.google.com/support/release-notes/js#version_930_-_november_04_2021) introduced reCAPTCHA Enterprise in 9.3.0, and the [official 9.6.1 App Check module](https://www.gstatic.com/firebasejs/9.6.1/firebase-app-check.js) exports `ReCaptchaEnterpriseProvider`. Following the [current Enterprise web setup guide](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider), initialization runs on the same Firebase app before Firestore/Auth/Functions initialization; token auto-refresh is enabled. Creation explicitly awaits `getToken` before the callable SDK attaches its attestation. Missing configuration, initialization failure or token failure blocks creation with a safe error; catalog/receipt reads do not use the creation gate.

The browser persists `{requestId, receiptToken, signature, revision}` in **sessionStorage only**, under `mammothCommerceAttempt:<card|preorder>:<randomRequestId>` plus an active-ID pointer. `signature` freezes the input snapshot for equality checks. The client issues the 64-lowercase-hex token from 32 CSPRNG bytes before the first network call; unchanged retries and reloads keep both identifiers. A successful creation response must echo exactly the issued proof; missing/mismatched proof never mounts card fields, reports pickup success, or replaces the original token. Pending legacy attempts without their own proof remain blocked for owner reconciliation. Confirmed receipts keep the same token in session storage and fragment-only receipt links; no proof enters local cached orders, URL queries, or application error logging. Session storage contains private attempt data and disappears with the browsing session; there is no public recovery after capability loss.

## Frontend integration (stable contract)

- `createPaymentIntent({requestId, receiptToken, cart, customerName, customerEmail, fulfillmentMethod, marketId?, pickupDate?, deliveryAddress?})` → `{orderId, orderName, receiptToken, clientSecret, totalAmount}`. Full order is saved BEFORE Stripe. `cart` is `{productId: positiveIntegerQuantity}` (maximum 12 jars). Fulfillment is `market_pickup` or `local_delivery`. Persist a cryptographically random UUID `requestId` per attempt and reuse it unchanged on retries. Prices/status/fees supplied by browser are ignored. Changed payload for same requestId is rejected. Client supplies the pre-persisted 32-byte receipt capability. Both initial success and valid replay echo that same supplied `receiptToken`; it is never generated/recovered from order ID, email or requestId. Replay without matching capability rejects before returning any client secret.
- `createPreorder({requestId, receiptToken, cart, customerName, customerEmail, fulfillmentMethod, marketId?, pickupDate?, specialNotes?, paymentMethod})` → `{orderId, orderName, receiptToken, totalAmount, emailState}`. `paymentMethod: pickup` requires `market_pickup`; `special_order` requires `special_order` and notes ≥10 characters. No client card confirmation/intent ID accepted here. `emailState: pending` means saved, NOT delivered; never promise an email was sent based on this response.
- `getGuestReceipt({orderId, token})` → `{orderId, orderName, status, paymentMethod, fulfillmentMethod, items, subtotal, discountAmount, deliveryFee, totalAmount, currency, marketName, pickupDate, deliveryDate, checkoutUrl}`. Never returns customer email/name/address/notes, token hash, internal IDs or webhook metadata. Receipt expires in 30 days and is revocable. Store token locally only if necessary; share receipt using `/receipt.html#order=ENCODED_ID&token=ENCODED_TOKEN`, NEVER query parameters, analytics, logs, or email subjects. Set Referrer-Policy: no-referrer on receipt page.
- `getDeliveryQuote({cart, address})` → `{deliveryFee, deliveryDate, subtotal, discountAmount, totalAmount, currency}`. Date is server-calculated next Monday in UTC with configured cutoff hours. Display result, do not calculate authoritative fees/date in browser.
- Public Firestore `settings/delivery` can be read; writes forbidden. Configuration schema below. Missing/disabled/incomplete policy rejects delivery.
- `reviewSpecialOrder({orderId, decision: 'approve'|'decline', items?, totalAmount?})` requires Firebase custom claim `admin === true`. Approve requires explicit `items: [{productId,name,quantity,price}]`, `totalAmount` equal to sum(quantity*price), all cents; owner supplies negotiated authoritative values, not customer. Returns `{orderId,status,checkoutUrl}`; approved status is `awaiting_payment`. Repeating identical approval retries checkout/email; conflicting decision or changed approved terms rejects. Decline returns `checkoutUrl: null`. No payment before approval.
- `resumePaymentSetup({orderId})` (admin claim) resumes checkout for a frozen approved special order, using only stored negotiated terms and the original provider idempotency key. Request-supplied items/total are ignored. It cannot approve an unreviewed request, alter terms, or resume a settled/declined order. The callable binds payment and mail secrets.
- `retryOrderEmail({orderId})` (admin claim) retries durable checkout-link email delivery. Without a hosted session **and** URL on an approved special order, returns `{orderId,delivered:false,suppressed:true}` without sending or claiming delivery; use `resumePaymentSetup`, not repeated mail retries. `revokeGuestReceipt({orderId})` (admin claim) revokes guest access.

`requestId` is required (16–128 characters, letters/digits/hyphens/underscores). No client operation marks paid. Receipt can show pending until signed webhook arrives. Callable failures use Firebase codes unauthenticated, invalid-argument, failed-precondition, permission-denied, not-found, unavailable, resource-exhausted; show a useful error without leaking customer data.

## Configuration / deployment handoff (no deployment performed)

Secret bindings: STRIPE_SECRET, STRIPE_WEBHOOK_SECRET, GMAIL_PASS. Non-secret environment: COMMERCE_PAYMENTS_ENABLED, COMMERCE_EMAIL_ENABLED, GMAIL_EMAIL, GMAIL_LOGIN_USER (optional), COMMERCE_ORIGIN (HTTPS origin). Checkout redirects are generated ONLY from that configured HTTPS origin, never a request URL. Configure Stripe webhook to `stripeWebhook` for `payment_intent.succeeded` and `checkout.session.completed`; async payments are disabled for approval checkout (card only). Use test mode first.

Both enable flags default to disabled unless exactly `true`. With flags absent/false, deployment declares no missing secret bindings; pickup and special requests remain independent of payment/mail secrets but now require correctly configured App Check. Owner declines, delivery quotes, and capability receipts retain their existing authorization without App Check. Card setup/approval fail with a safe configuration error; the webhook returns 503; mail triggers leave durable pending work untouched. The frontend must say the request is saved, not that a notification was delivered. Owner queue uses persisted `emailState` (`pending`, `sending`, `sent`) and `retryOrderEmail` after configuration.

For authorized deployment, provision **rotated** Stripe secret and endpoint signing secret directly in Secret Manager through trusted Firebase tooling, never chat/source/browser client code. Provision the Gmail app password separately. Only then set the corresponding flags in the functions deployment dotenv configuration (for example `.env.PROJECT_ID`, uncommitted); deploy the functions that bind those secrets. Do not enable flags with nonexistent secret versions: Firebase will need those versions. No `functions.config()` or legacy runtime configuration is read. Secrets are accessed lazily at invocation time. This implementation uses explicit `firebase-functions/v1` and the existing dependencies; no package upgrade was necessary.

`settings/delivery` illustrative schema, **not an established service-area promise or live configuration**: `{enabled:true, allowedZips:['32202'], state:'FL', feeCents:500, minimumJars:5, cutoffHours:48}`. Exact US ZIP/state allowlist; complete street/city/state/zip required. Monday is UTC calendar Monday 00:00, cutoffHours before it; after cutoff moves to following Monday. All fields required; no silent free delivery/geography defaults. `feeCents` must be nonnegative integer, `minimumJars` 5–12, `cutoffHours` integer 0–168. Zero fee/cutoff must be explicit. Server owns fee/date at order creation, independent of later settings changes. Quote is informational, not a reservation: order creation re-reads the current policy and product prices in its transaction.

Security collections `orders`, `stripeEvents`, `paymentBindings` are server-write-only. Orders only readable by authenticated owning user/admin; guest access only via allowlist callable. No admin browser direct updates, even status edits. No live writes, deployment, Stripe or mail verification is included in local tests.

## Order lifecycle and recovery

| Flow | Creation | Allowed transition | Payment confirmation |
| --- | --- | --- | --- |
| Pickup, pay there | `pending` | No client lifecycle writes | Not represented as card-paid |
| Ordinary card | `awaiting_payment` BEFORE Stripe call | Immutable amount/currency/customer/fulfillment snapshot | Signed bound intent → `paid` or `paid_requires_review` (market capacity/schedule conflict) |
| Special request | `awaiting_approval`, no payment object | Admin `decline` → `declined`, or explicit final terms → `awaiting_payment` and hosted Checkout | Signed bound intent/session → `paid` |

`requestId` is an idempotency identifier, not authorization: generate it using `crypto.randomUUID()`, not a counter/name/email. The independent `receiptToken` is the mandatory authorization proof for creation replay. The order ID is SHA-256 of `requestId`, not of the receipt capability. A canonical payload fingerprint includes customer identity, authenticated UID, cart, fulfillment and payment path. Same ID plus changed payload is a conflict, not an edit. Both creation responses include the persisted authoritative `orderName`, including retries; the frontend must display it rather than an invented local adjective name. New amounts require a deliberately new request after reconciliation; do not automatically create new IDs after provider/network errors.

Transactions read product/promotion/market/delivery state and abuse budgets before any writes. **Unpaid card orders never reserve market capacity.** Provider outage, process crash and abandoned card checkout therefore hold no slot and need no expiry scheduler. Pickup pay-there preorders are actual accepted reservations: their creation transaction increments configured capacity; their abandonment/cancellation remains owner-managed. Card fulfillment reserves a slot only in the verified settlement transaction; a race with another paid order or pickup preorder never exceeds configured capacity. If full, closed, past cutoff, rolled over or no longer correctly configured, settlement is still recorded as `paid_requires_review` with `reconciliationRequired:true`, `reviewReason`, payment binding/event and paid timestamp, but does not increment capacity. This is **money received, fulfillment NOT confirmed**: customer/operations email explicitly requests manual review, never another payment. The owner must contact the customer and arrange an explicitly approved alternative or a provider refund; there is no automatic refund, reconciliation API or automatic promotion from review to fulfilled. Duplicate settlement events preserve review state and do not reserve again or enqueue duplicate mail. A durable pending outbox exists even if SMTP is disabled, but it is not a guaranteed immediate alert. Do not fulfill any `paid_requires_review` order from a generic paid filter.

A lease prevents concurrent provider calls, with a stable Stripe idempotency key as crash-retry protection. Provider failures release the lease; process crashes require waiting up to two minutes before retry. Unbound setup older than 23 hours fails closed for owner reconciliation instead of reusing a potentially expired provider idempotency key and creating another charge. Existing hosted Checkout sessions are never silently replaced; expiry/cancellation requires explicit owner reconciliation outside this API.

Webhook verifies the signature using the untouched `request.rawBody`, then transactionally verifies order ID, random binding metadata, amount/currency, successful settlement, intent uniqueness, and (for session events) exact session ID. Event ID plus payload digest is durably recorded in the same transaction as `paid`; identical retries are acknowledged, mutated event-ID replays rejected. A second valid event for the same payment does not enqueue another confirmation. Signature/mismatch events never record success. Infrastructure failures return non-2xx for Stripe retry. No fulfillment is inferred from a redirect, browser result, email send, or admin's approval.

Receipt capabilities are 32 client-CSPRNG bytes encoded as 64 lowercase hex characters, generated and persisted locally BEFORE the first creation request. Only their SHA-256 hash is stored; raw tokens are never stored server-side, logged, emailed, or sent to Stripe. Expiration is 30 days from creation; revocation and expiry also deny creation replay. Provider failure after persistence or a lost first response no longer loses the capability: retry with the identical token, requestId, frozen payload and original authenticated UID (or original guest identity). Constant-time hash comparison plus canonical payload/UID fingerprint must both match before returning the supplied token or any provider client secret. Changed/missing tokens cannot replace a committed hash, including on transaction retries. Local capability loss has no public recovery/reissue endpoint: use owner reconciliation/authenticated existing order access, never automatically create a second payment. Legacy 43-character base64url receipt tokens remain valid only for capability-proven receipt reads until expiry/revocation; existing orders with unknown/missing hashes or missing expiry cannot obtain a new capability through creation. No historical migration is performed.

Approval checkout redirects contain only `#order=...`; the browser can restore its locally retained token. Emailed hosted Checkout URLs are separate payment capabilities and do not contain the guest receipt token. Review returning a checkout URL proves only that checkout was created, not mail delivery or payment. Approved negotiated items replace the request estimate only during the admin review transition; subsequent conflicting terms are rejected. Provider failure leaves the frozen approval in `awaiting_payment` with `emailState: blocked_payment_setup`; the email worker suppresses all payment demand until both session ID and URL are durably present. `resumePaymentSetup` retries the same frozen approval without the owner re-entering item lines. The 23-hour unbound retry deadline and 2-minute crash lease still apply; after that, manual provider reconciliation is required. A pending special request never uses pickup/pay-at-pickup wording.

Emails use a versioned durable outbox on the order, short processing lease, attempt count, and sent version. Create/update triggers retry failures; `retryOrderEmail` provides an authenticated owner retry. Customer and operations get separate SMTP messages. Customer input is a bare ASCII single mailbox (no display names, address lists, whitespace, CRLF or multiple `@`); delivery revalidates stored addresses too and passes Nodemailer `{address: customerEmail}`, never an untrusted address-list string. SMTP delivery is **at least once**, not exactly once: a crash after SMTP accepts a message but before recording the sent version, or a failure sending the second recipient, may duplicate mail on retry. It cannot duplicate the charge or paid transition. Mail and payment provider errors never leak their provider payloads to public callers.

Order timestamps are server-generated epoch milliseconds (`createdAt`, `paidAt`, `approvedAt`); date-only values are ISO `YYYY-MM-DD`. Existing historical order records without this schema are not automatically migrated or granted guest access. There is no new client endpoint for arbitrary order status changes.

## Pickup schedule and occurrence configuration — publish gate

**Do not publish pickup changes against the currently observed name-only live markets without owner-approved schedule configuration.** The parent agent's read-only public REST inspection found only `name` among the relevant fields on `market_atlantic`, `market_murray`, `market_palm`, and `market_ponte_vedra`; no authoritative weekday/day, timezone, approved pickup dates, capacity or cutoff was established. Those records intentionally fail closed here. No live data was changed. Neither market names such as “(Sundays)” nor browser ID-to-weekday fallback maps are authority for backend scheduling. Local `ui.js` currently renders `market.weekday ?? weekdayByMarket[market.id]`, and `app.js` uses that option's weekday to suggest a date; this is only a browser suggestion and does not supply missing server configuration. `app.js` was not changed (approval gate).

Owner-confirmed market fields (schema only, **not proposed live business values**):

- `timezone`: required valid IANA timezone string. Future/today comparisons use the market's local calendar, not the caller's timezone or UTC midnight. Same-local-day pickup is not accepted in this phase.
- Either `pickupDates`: a nonempty list of exact approved valid `YYYY-MM-DD` calendar dates, **or** `weekday` / legacy `day`: integer 0–6 (Sunday–Saturday). If explicit dates are provided they take precedence and malformed dates reject the configuration. Without explicit dates only the canonical **next** weekday strictly after local today is accepted, not an arbitrary later week. If both weekday and day are present, they must agree. No schedule is inferred from names or market IDs.
- Existing `capacity`, `reservedCount`, and `orderCutoffAt` are preserved, not silently reset. Any positive capacity/count or supplied cutoff requires `occurrenceDate` exactly equal to the selected pickup date. Capacity/count, if present, must be nonnegative safe integers. Missing capacity or explicit zero retains the existing unlimited/no-enforced-capacity behavior; it is not a verified operational promise. A positive capacity counts **orders, not jars**. Missing count means zero only for correctly scoped configured capacity.
- `orderCutoffAt`, when supplied, must be a parseable timestamp with explicit `Z` or numeric timezone offset; equality with now is closed. It applies only to `occurrenceDate` and is checked both before checkout and at settlement. A late settlement is review-held, not discarded.

**Safe limited phase:** with capacity/cutoff enabled, this API supports exactly one configured `occurrenceDate` per market at a time; it intentionally refuses other dates even if listed in `pickupDates`. The owner must close/reconcile the old occurrence, account for accepted pickup reservations and paid orders, then explicitly approve the next occurrence's date/count/capacity/cutoff. There is no scheduler, automatic counter reset, inferred cancellation or per-date ledger migration. Before upgrading an already-used older implementation, reconcile any existing counters that included unpaid cards and all outstanding provider objects; do not reset a live count blindly. Late old payments are review-held and cannot consume the new occurrence's count. Introducing capacity to a previously unlimited occurrence also requires reconciling its accepted orders first.

## Abuse budgets and operational limits

Neither `rawRequest.ip` nor any forwarding header is used as an abuse/security identity. Express trust-proxy does not prove a Google ingress chain, so no per-IP limit or spoof-proof network identity is claimed. Both creation entrypoints require SDK-verified App Check, then transactionally enforce server-only `commerceRateLimits` budgets: 3 fresh orders per normalized-email hash bucket and a 1,000-order global circuit breaker per 15-minute window starting at each budget's first accepted creation. The global cap replaces the previous overly small 100-order shared cap; it is a coarse emergency cost ceiling, not fair per-customer throttling. These are code safety budgets, not live business settings. Email bucket keys use the first four SHA-256 hex characters and fixed `v2-email-` namespace; distinct colliding emails share the cap conservatively. The namespace is bounded to 65,536 email bucket documents plus one `v2-global` document without a TTL/scheduler. Existing pre-v2 limiter documents are unused but not automatically removed; their cleanup requires owner approval. Raw email/IP/token values are not stored in limiter documents; hashes are not anonymization against guessing. Only creation commits charge budgets; capability-proven identical retries do not. Provider failures after persistence consume the one original creation budget. Declines, quotes, receipt reads, admin recovery and settlement do not consume creation budgets. The current rules' implicit deny covers this private collection; verify deployed rules before publish.

App Check attests the registered app, NOT a human, unique device, email ownership or trustworthy shopper; normal tokens may be replayed until expiry. No consumed/limited-use token mode is enabled. A distributed actor with valid attestation can still rotate emails, exhaust shared buckets/global capacity, contend on the global Firestore counter, and create accepted pay-there reservations over time. Targeted email/bucket denial remains possible because email ownership is not verified; fixed bucket collisions introduce additional conservative false positives. App Check and these caps are not complete DDoS/cost protection or a guarantee of availability. Review the circuit-breaker value against actual observed traffic/costs before publish; no production sizing benchmark was performed. Idempotent provider retries are lease-protected but not charged as new orders. No edge rate limiting, scheduler, cancellation/release endpoint, automatic refund or provider reconciliation automation is claimed. Owner monitoring of review-held payments and abandoned pay-there reservations is required before enabling paid pickup. UI support for displaying `paid_requires_review` safely, resuming frozen approval setup, and displaying returned `orderName` must be reviewed separately; this backend task does not bypass the `app.js` approval gate.

## Official Firebase references checked for this change

- [App Check enforcement for callable Cloud Functions](https://firebase.google.com/docs/app-check/cloud-functions): current official first-generation example uses `require("firebase-functions/v1")`, `runWith({enforceAppCheck:true})`, and verified `context.app`. SDK callables attach tokens automatically; consumed-token replay protection is a separate opt-in and is not enabled here.
- [v1 CallableContext reference](https://firebase.google.com/docs/reference/functions/firebase-functions.https.callablecontext): `app` is decoded **and verified** App Check data; `rawRequest` is just the raw HTTP request, not a documented nonspoofable identity boundary.
- [Web reCAPTCHA Enterprise provider](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider): register/provision the app and site key, initialize the provider on the Firebase app and explicitly enable auto-refresh. No production key, approved domains, registration or valid live attestation was established in this task.
